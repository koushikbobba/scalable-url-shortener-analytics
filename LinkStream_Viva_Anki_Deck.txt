<b>Q1: What is LinkStream, and what core problem does it solve?</b>	LinkStream is a scalable, event-driven URL shortener and link analytics platform. It solves the performance bottleneck of traditional shorteners by decoupling high-speed HTTP redirection (sub-10ms) from synchronous analytics database writes using Redis caching and Apache Kafka streaming.	LinkStream::General-Viva
<b>Q2: What is the primary technology stack used in the backend?</b>	Python 3.11, Django REST Framework 5.0, PostgreSQL 16, Redis 7.2, Apache Kafka 3.7 (KRaft mode), Celery 5.3, Gunicorn, and Docker Compose.	LinkStream::General-Viva
<b>Q3: How does the system achieve sub-10ms URL redirection?</b>	By utilizing a Redis Cache-Aside pattern. When a request hits <code>GET /{short_code}</code>, the application checks Redis first. If found (Cache Hit), it returns an immediate <code>302 Found</code> redirect without querying PostgreSQL.	LinkStream::Core-URL-Engine
<b>Q4: Why does the redirect endpoint return an HTTP `302 Found` status code instead of HTTP `301 Moved Permanently`?</b>	HTTP 301 is cached permanently by client browsers, preventing subsequent clicks from reaching our server. HTTP 302 forces the browser to hit our server on every click, allowing us to accurately track real-time analytics.	LinkStream::Core-URL-Engine
<b>Q5: What happens if a user requests a short URL that does not exist?</b>	"The system returns an HTTP <code>404 Not Found</code> JSON error response. To prevent Cache Penetration attacks, the system caches a short-lived negative result (<code>{""not_found"": True}</code>) in Redis for 60 seconds."	LinkStream::General-Viva
<b>Q6: You mentioned Cache Penetration. What is the difference between Cache Penetration, Cache Avalanche, and Cache Stampede?</b>	- <b>Cache Penetration:</b> Requests for non-existent keys bypass the cache and repeatedly hit the DB. Solved by negative caching or Bloom Filters.<br>&bull; <b>Cache Avalanche:</b> Many cached keys expire simultaneously, causing a massive surge of DB queries. Solved by adding random jitter to TTLs.<br>&bull; <b>Cache Stampede (Thundering Herd):</b> High concurrency requests hit a single expired key concurrently, causing multiple workers to compute the same DB query. Solved by distributed locks (<code>SET NX</code>).	LinkStream::Redis-Caching
<b>Q7: How does your system specifically prevent Cache Stampedes?</b>	In <code>LinkService.get_destination()</code>, when a cache miss occurs for a popular short code, workers attempt to acquire a short-lived Redis lock (<code>ratelimit:lock:{short_code}</code>). Only the worker that acquires the lock queries PostgreSQL and populates the cache; other workers wait 50ms and retry Redis.	LinkStream::Redis-Caching
<b>Q8: What algorithm is used to generate short codes in LinkStream?</b>	Base62 encoding using characters <code>[0-9a-zA-Z]</code>.	LinkStream::Core-URL-Engine
<b>Q9: Why did you choose a length of 7 characters for auto-generated short codes?</b>	A Base62 string of length 7 provides $62^7 = 3,521,614,606,208$ (~3.52 Trillion) unique combinations. Even at 1,000 links per second, it would take over 110 years to exhaust the keyspace.	LinkStream::Core-URL-Engine
<b>Q10: How does the system handle short code collisions when two users create links simultaneously?</b>	The database column <code>short_code</code> has a <code>UNIQUE</code> constraint index. In <code>LinkService.create_link()</code>, the operation is wrapped in a <code>transaction.atomic()</code> block. If concurrent generation produces a duplicate code, an <code>IntegrityError</code> is caught, triggering an automatic retry with fresh random entropy.	LinkStream::Core-URL-Engine
<b>Q11: What is a custom alias, and how is it validated?</b>	A custom alias allows users to specify their own short code (e.g., <code>link.io/my-portfolio</code>). It is validated via regex <code>^[a-zA-Z0-9_-]+$</code>, checked against reserved keywords, verified for length (3–64 chars), and checked for uniqueness in PostgreSQL.	LinkStream::Core-URL-Engine
<b>Q12: What reserved keywords are protected from custom alias creation?</b>	Routes such as <code>admin</code>, <code>api</code>, <code>health</code>, <code>metrics</code>, <code>swagger</code>, <code>docs</code>, <code>login</code>, <code>register</code>, <code>static</code>, and <code>media</code>.	LinkStream::Core-URL-Engine
<b>Q13: How does the system handle link expiration?</b>	The <code>Link</code> model includes an <code>expires_at</code> timestamp. The redirect view checks if <code>expires_at</code> is present and if <code>timezone.now() > expires_at</code>. If expired, it returns HTTP <code>410 Gone</code>. A Celery Beat task also periodically purges expired Redis keys.	LinkStream::General-Viva
<b>Q14: How does the system handle disabled links?</b>	The <code>Link</code> model has an <code>is_active</code> boolean field. If <code>is_active=False</code>, <code>RedirectShortCodeView</code> returns HTTP <code>404 Not Found</code> with a message stating the link was disabled by the owner.	LinkStream::General-Viva
<b>Q15: Why did you use Apache Kafka instead of RabbitMQ or Celery for click analytics?</b>	Click analytics are high-volume, log-append time-series events. Kafka supports persistent, disk-backed topic partitions, consumer group offset tracking, and event replayability. RabbitMQ and Celery are task queues designed for message destruction upon task acknowledgment.	LinkStream::Kafka-Pipeline
<b>Q16: Kafka guarantees At-Least-Once delivery. How do you handle duplicate click events in your consumer?</b>	We achieve idempotency in the consumer by assigning a unique signature <code>(link_id, ip_hash, rounded_minute_timestamp)</code> to each event or performing bulk insertion using <code>ON CONFLICT (link_id, ip_hash, clicked_at) DO NOTHING</code> in PostgreSQL.	LinkStream::Kafka-Pipeline
<b>Q17: What is KRaft mode in Kafka 3.7, and why is it used instead of Zookeeper?</b>	KRaft (Kafka Raft Metadata mode) manages Kafka cluster metadata internally using an event-driven consensus protocol. It eliminates the operational overhead, memory consumption, and latency of running an external Apache Zookeeper cluster.	LinkStream::Kafka-Pipeline
<b>Q18: What is consumer lag in Kafka, and why is it an important metric?</b>	Consumer lag is the delta between the latest offset published to a Kafka topic partition and the offset currently processed by the consumer group. High consumer lag indicates that consumer workers are falling behind input traffic.	LinkStream::Kafka-Pipeline
<b>Q19: How are click events batch-processed into PostgreSQL?</b>	The standalone Python consumer (<code>kafka_pipeline/consumer.py</code>) polls Kafka for up to 500 records. It parses the events, constructs a list of <code>ClickEvent</code> model instances, and executes <code>ClickEvent.objects.bulk_create(batch, batch_size=500)</code> inside a single atomic transaction.	LinkStream::Postgres-Analytics
<b>Q20: How are total click counts updated on the `Link` model during batch ingestion?</b>	Rather than executing separate <code>UPDATE</code> queries, the consumer aggregates click counts per <code>link_id</code> in a Python <code>Counter</code> and executes atomic SQL counter increments using <code>Link.objects.filter(id=link_id).update(click_count=F('click_count') + count)</code>.	LinkStream::General-Viva
<b>Q21: What is the purpose of Django's `F()` expressions in `update(click_count=F('click_count') + count)`?</b>	<code>F()</code> expressions perform database-level atomic operations directly in SQL (<code>UPDATE links SET click_count = click_count + N</code>) without pulling model instances into Python memory, avoiding race conditions under concurrent updates.	LinkStream::General-Viva
<b>Q22: How does LinkStream ensure GDPR compliance regarding client IP addresses?</b>	Client IP addresses are never stored in raw text. <code>hash_ip()</code> computes a salted SHA-256 hash (<code>sha256(ip + salt)[:32]</code>). This allows exact distinct count unique visitor calculations (<code>COUNT(DISTINCT ip_hash)</code>) without storing Personally Identifiable Information (PII).	LinkStream::General-Viva

LinkStream::General-Viva
<b>Q25: What is Server-Side Request Forgery (SSRF), and how does LinkStream prevent it?</b>	SSRF occurs when an attacker submits a URL that causes the server to issue HTTP requests to internal networks. <code>is_ssrf_safe_url()</code> validates that the protocol is strictly <code>http</code> or <code>https</code> and rejects local loopback (<code>127.0.0.1</code>), private RFC1918 subnets (<code>10.0.0.0/8</code>, <code>192.168.0.0/16</code>), and cloud metadata IP addresses (<code>169.254.169.254</code>). <b>Q27: How does your rate limiter prevent Denial of Service (DoS) attacks?</b>	<code>SlidingWindowRateLimiter</code> uses a Redis Sorted Set (<code>ZSET</code>) to enforce request quotas (30 req/min for anonymous users, 120 req/min for authenticated users). If quota is exceeded, HTTP 429 is returned.	LinkStream::Security-RateLimiting
<b>Q28: How does the Redis ZSET sliding window algorithm work step-by-step?</b>	1. Key format: <code>ratelimit:{action}:{identifier}</code>.<br>2. <code>ZREMRANGEBYSCORE</code> removes timestamps older than <code>(now - 60s)</code>.<br>3. <code>ZCARD</code> counts remaining members in the rolling window.<br>4. If count $\ge$ limit, request is rejected.<br>5. Else, <code>ZADD</code> current Unix timestamp with a unique member ID and set key TTL to 65s.	LinkStream::Redis-Caching
<b>Q29: What happens to rate limiting if Redis crashes?</b>	<code>SlidingWindowRateLimiter</code> catches Redis connection exceptions and fails open gracefully (or switches to an in-memory sliding window dictionary fallback), logging a warning while ensuring service uptime.
